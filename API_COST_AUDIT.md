## Возможные причины перерасхода

1. **Личный ключ мог использовать внешний клиент.** Тарификация Astra с длинным контекстом и объём кэша согласуются с повторной отправкой длинного контекста, например агентной задачей в IDE. Возможны прежняя конфигурация VS Code, другое расширение, другая машина или другой API-клиент. Название `vsCode` не устанавливает приложение. Playground также учитывается как API-использование. [Разбор неизвестной активности OpenAI](https://help.openai.com/en/articles/10478918-reviewing-api-usage-and-costs).
2. **Личный ключ вручную использовался в Garmin.** Один аккаунт Garmin хранит один OpenAI-ключ для всех четырёх пресетов, но разные аккаунты и базы могут хранить разные ключи. OpenAI относит расходы к владельцу фактически использованного ключа. Истории заменённого значения в схеме приложения нет. Наличие старого локального комментария и отличающегося ключа в SQLite подтверждает два локальных значения, но не использование обоих текущим кодом.
3. **Несколько генераций внутри Garmin.** Повторные нажатия из разных окон, повтор календарного разбора при смене настройки и многошаговые ответы с инструментами способны увеличить расходы. Привязать к ним $19,69 по нынешним логам нельзя.
4. **Чужое использование личного ключа.** Возможно, если ключ был отдельно скопирован, экспортирован, передан, сохранён в другом аккаунте Garmin или использован через скомпрометированный аккаунт или машину. Проверенные Git, публичный JS, доступные истории и штатный механизм запроса такого пути не показали.
5. **Прошлый вход Codex через API-ключ.** Сейчас локальные метаданные и `codex login status` подтверждают вход через ChatGPT. Режим API-ключа тарифицируется отдельно от подписки. Текущий режим не устанавливает историю прежних входов, других профилей и установок, а настройка модели в Codex не определяет способ оплаты. Наличие именно Plus по локальному конфигу не проверено. [Аутентификация Codex](https://learn.chatgpt.com/docs/auth#openai-authentication).

## Подтверждённые факты и неподтверждённые гипотезы

### Откуда берётся ключ и кто его получает

- `PUT /api/account/keys/openai` принимает значение от вошедшего пользователя при сохранении. Поле ввода маскируется, значение хранится в состоянии формы до сохранения и отправляется в собственный API по HTTPS в продакшене. В локальном Docker фронтенд доступен по loopback. При обычном использовании консультанта браузер ключ повторно не отправляет. [Форма ключа](frontend/src/components/AccountPanel.jsx#L26), [сохранение](backend/accounts.py#L252), [Docker Compose](docker-compose.yml#L19).
- Сервер шифрует ключ Fernet с `SECRETS_ENCRYPTION_KEY` и хранит в `coach_settings.openai_key` по `user_id`. Генерация расшифровывает только запись текущего аккаунта. Запись приложения содержит один OpenAI-ключ и отдельно ключ GigaChat. В актуальном коде отсутствует чтение `OPENAI_API_KEY` для тренера и переход на чужой или глобальный ключ. `DATABASE_URL` и его алиасы определяют серверную БД, `SQLITE_PATH` — локальную. `BACKEND_ORIGIN` направляет прокси к бэкенду, `VITE_PUBLIC_DEMO` включает демо. [Шифрование и сессии](backend/accounts.py#L49), [выбор ключа](backend/main.py#L46), [хранилище](backend/store.py#L301), [конфигурация](backend/settings.py#L29), [прокси](frontend/api/backend.js#L4).
- Сессия проверяется по хэшу cookie и сроку действия. Middleware устанавливает ID этого аккаунта для защищённых маршрутов. Cookie `HttpOnly`, `SameSite=Lax`, на HTTPS — `Secure`. Изменяющие запросы проверяются по `Origin`, когда он передан. API статуса возвращает булевы признаки наличия ключей, модель и пресет. Хранимый ключ приложение использует только в заголовке запроса OpenAI, который собирает серверный адаптер. [Middleware](backend/main.py#L160), [cookie](backend/accounts.py#L69), [поиск сессии](backend/store.py#L269), [Origin и ошибки валидации](backend/request_security.py#L11), [ответ аккаунта](backend/accounts.py#L209), [заголовок OpenAI](backend/providers/openai.py#L42).
- Другой аккаунт дашборда по штатному пути получит собственный ключ. Для использования того же ключа его нужно отдельно сохранить в том аккаунте или получить доступ к исходной сессии. В собственном браузере тело запроса при **вводе нового ключа** может быть видно в DevTools, расширению с доступом или при экспорте HAR. Если пользователь вручную вставит секрет в вопрос консультанту или описание Garmin, обычная обработка текста может передать его модели в контексте этого аккаунта. Проверка текста на секреты перед отправкой отсутствует. Для диагностики достаточно имени или ID ключа.

**Автоматизация и повторы.** В Git нет Cron, CI-задачи или таймера, который сам запускает OpenAI. Таймер обновляет погоду, FastAPI `BackgroundTasks` используется для письма восстановления. JS-обёртка POST и Vercel-прокси выполняют один сетевой вызов за обращение без собственного retry. OpenAI-адаптер имеет конечный цикл из четырёх шагов с проверкой дедлайна и максимум одним дозавершением при неполном или пустом ответе при наличии времени. Функции отправляются на первых трёх шагах, параллельные function calls выключены. Длинные вызовы инструментов и таймаут ответа могут привести к ручному повтору пользователем. Внешние расписания и прошлые запросы по статике определить нельзя. [POST клиента](frontend/src/lib/coachRequest.js#L1), [прокси и таймаут](frontend/api/backend.js#L22), [OpenAI-цикл](backend/providers/openai.py#L49), [фоновое письмо](backend/accounts.py#L175).

**Кэш.** Сводки сохраняются по дню и диапазону в БД аккаунта, до 12 записей. При чтении учитываются версия контекста, модель, пресет и ревизии Garmin и плана. Сохранённый разбор хранится по ID тренировки и содержит автора-модель, пресет и дату. Повтор генерации явным POST начинает новый запрос даже при готовом результате. Дедупликация сводки в `pending` охватывает только одну копию интерфейса. Отдельно у OpenAI есть автоматический prompt cache, который удешевляет повторный префикс. Он совместим с отправкой `store: false` и продолжает учитывать чтение и запись токенов. [Сводка](backend/main.py#L528), [разбор](backend/main.py#L628), [состояние клиента](frontend/src/hooks/useCoachSummary.js#L26), [Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching).

**Объём контекста.** Бэкенд обрабатывает выбранный и предыдущий периоды, отправляет агрегаты и до четырёх недель, две последние пробежки с описаниями до 400 символов, при подходящем дневном сценарии до пяти силовых с описаниями до 400, до восьми фактов сегодняшнего дня, сводные данные восстановления, цель и план. Из 60 сохранённых реплик в срез попадают четыре для сводки, шесть для разбора и восемь для обычного чата. Отправляемые реплики сокращаются до 350 символов каждая. При вопросе могут добавляться фрагмент текущей сводки и результаты инструментов. Разбор ограничивает инструменты чтением, например до 12 сплитов или до семи дней отдельной метрики. Полная история Garmin, сырой FIT и GPS-трек не входят в базовую посылку. Единого измеряемого потолка входных токенов и суммарного размера ответов инструментов нет. [Контекст запроса](backend/coach_analysis.py#L49), [промпт и реплики](backend/coach.py#L159), [агрегаты бега](backend/coach.py#L292), [дневной контекст](backend/coach_context.py#L74), [инструменты](backend/coach_tools.py#L108).

## Оценка стоимости одного обращения

Тарифы Standard для короткого контекста, USD за 1 млн токенов на дату аудита. OpenAI тарифицирует обычный вход, чтение и запись кэша по отдельным ставкам. Запись 30 минут используется по умолчанию на этих моделях, ставки записи заменяют цену обычного входа для этих токенов. В выход входят reasoning-токены. Расчёт для одного действия суммирует все вызовы адаптера. [GPT‑6.2 Sol](https://developers.openai.com/api/docs/models/gpt-6.2-sol), [GPT‑6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna), [GPT‑6.2 Astra](https://developers.openai.com/api/docs/models/gpt-6.2-astra), [Расчёт кэша](https://developers.openai.com/api/docs/guides/prompt-caching), [Reasoning и выходные токены](https://developers.openai.com/api/docs/guides/reasoning).

| Модель | Обычный вход | Чтение кэша | Запись 30 мин | Выход | Пример 2 000 входа + 500 выхода | Пример 15 000 входа + 3 000 выхода за несколько шагов |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| GPT‑6.2 Sol Light / Medium | $2 | $0,10 | $2,50 | $10 | $0,009 | $0,060 |
| GPT‑6 Luna | $0,10 | $0,01 | $0,125 | $0,50 | $0,00045 | $0,003 |
| GPT‑6.2 Astra | $8 | $0,40 | $10 | $40 | $0,036 | $0,240 |

Примеры в двух правых столбцах считают полный вход по обычной ставке, без кэш-чтения и записи. Light и Medium имеют одну ставку, а итог может отличаться за счёт объёма reasoning. Код выставляет `max_output_tokens` 3 072 для обычного шага сводки или чата и 4 200 для разбора, с дозавершением до 4 096 или 5 600 соответственно. Это предел каждого шага, а не ожидаемый объём ответа.

**Фактические образцы из локальной БД за 25–27 ноября.** Одна сводка Sol — 3 285 входных и 529 выходных, около **$0,0119** при обычном входе. Два разбора Sol, сопоставленные с записью чата по уникальному совпадению ответа, — 11 310–11 410 входных и 447–484 выходных, около **$0,0274 за разбор** в среднем. Один разбор Luna — 11 539 входных и 313 выходных, около **$0,00131**. Это оценки по локальной выборке, не платёжные данные. Общий локальный счётчик за три дня содержит 175 696 токенов обоих провайдеров. Сравнить его напрямую с облачным счётом нельзя. [Агрегация расхода](backend/coach_usage.py#L6), [сохранение расхода](backend/main.py#L236).

**Что образовало фактический расход 27 ноября.** В разбивке Astra запись кэша стоила $7,22 для long context и $4,22 для обычного контекста, вместе **$11,44**. Ещё $3,27 приходится на чтение кэша в long context. Для позиции чтения кэша в обычном контексте сумма не указана в присланном фрагменте. На Astra тариф long context применяется к запросам с более чем 272 тыс. входных токенов. Ставки входа и кэша удваиваются, выхода повышаются в 1,5 раза. Следовательно, как минимум часть запросов была существенно крупнее локальных образцов тренера. [Правила тарификации GPT‑6.2 Astra](https://developers.openai.com/api/docs/models/gpt-6.2-astra).

## Рекомендации по сокращению расходов

1. Для обычного чтения открывать сохранённую сводку или разбор. Оставить повторную генерацию отдельным действием. На сервере объединять одновременные совпадающие генерации по аккаунту, модели, ревизии и параметрам запроса. Для чата учесть ID запроса, чтобы повтор доставки не отправлял вопрос модели дважды.
2. Закрыть повтор старого календарного разбора при пересоздании консультанта. Для нового запроса хранить явный ID и потреблять намерение один раз. Проверить сценарии смены модели и цели после разбора при помощи заглушки OpenAI.
3. Отдельно считать число шагов и фактические input, cached, cache-write, output и reasoning. Уменьшать бюджеты шагов на сводках и коротких ответах по имеющимся замерам. Для сравнения Luna, Sol Light и Astra использовать одинаковые сценарии и проверить качество предложений плана до смены модели по умолчанию.
4. Ограничить суммарный ввод, объём результатов инструментов и количество автоматических шагов на действие. Сохранять стабильный префикс для prompt caching после проверки корректности. Прекращать дозавершения по бюджету и времени. [Рекомендации по оптимизации кэша](https://developers.openai.com/api/docs/guides/prompt-caching#how-to-optimize-prompt-caching).

## Рекомендации по защите API

1. Единица изоляции расходов — отдельный OpenAI-проект для Garmin и выделенный сервисный ключ с нужными разрешениями. Сохранить раздельные ключи Garmin, IDE и других приложений. В текущей реализации ключ тренера задаётся на уровне аккаунта и хранится зашифрованным. Перенос в серверную переменную Vercel потребует отдельного изменения схемы, включая проверку, кто вправе расходовать общий ключ. Клиентские переменные для секретов не подходят. [Проекты, сервисные аккаунты и разрешения](https://help.openai.com/en/articles/9186755-managing-projects-in-the-api-platform).
2. Проверить состояние и дату включения `Enforce a hard limit` для `Default project`. Если он уже действовал в момент всплеска, передать в поддержку OpenAI настройки, сумму и период UTC. Принудительный лимит в проекте с несколькими ключами может остановить и другие клиенты этого проекта. Для отдельного проекта Garmin можно задать согласованный бюджет **$3–5 в месяц**, оповещения и принудительный предел. Параллельно добавить серверную частотную и суточную квоту на аккаунт, ограничение одновременных генераций и ответ `429` до обращения к провайдеру. [Лимиты и оповещения OpenAI](https://help.openai.com/en/articles/9186755-managing-projects-in-the-api-platform#set-spend-limits-and-alerts).
3. Журналировать время UTC, псевдоним аккаунта, назначение запроса, модель и пресет, безопасный идентификатор ключа, ID запроса OpenAI, токены по категориям, шаг и результат. Исключить заголовки авторизации, тела ввода ключа, личные данные и тексты тренировок из журналов и HAR для передачи. Хранить ключ шифрования отдельно от резервных копий БД.
4. Убрать устаревший открытый комментарий из локального `.env` после согласования. Если `vsCode` больше не используется или подтверждено неизвестное успешное использование, отозвать именно этот ключ в OpenAI, проверить зависимые клиенты и заменить активный ключ при необходимости. Удаление записи в Garmin или локальном файле само по себе не отзывает ключ в OpenAI. Добавить сканирование секретов перед коммитом. [Безопасность OpenAI API](https://help.openai.com/en/articles/8304786-keeping-your-openai-account-secure).
